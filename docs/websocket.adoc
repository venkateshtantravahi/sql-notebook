= WebSocket Query Execution
:toc: left
:toclevels: 3
:sectnums:
:source-highlighter: rouge

== Overview

The WebSocket module exposes a persistent, bi-directional connection at `ws://localhost:8080/ws/query`.
It allows the notebook frontend to submit SQL queries and receive live status updates without blocking or polling.

Unlike `POST /query` (which blocks until the query finishes), the WebSocket endpoint immediately pushes a `running` message, then pushes the final result asynchronously when the query completes. Multiple cells can be in-flight simultaneously on a single connection.

== Endpoint

[source]
----
ws://localhost:8080/ws/query
----

== Message Protocol

=== Browser → Server (Incoming)

[source,json]
----
{
  "cellId":    "cell-1",
  "namespace": "prod_pg",
  "sql":       "SELECT id, name FROM users LIMIT 10"
}
----

[cols="1,1,3"]
|===
| Field | Type | Description

| `cellId`
| String (required)
| Unique identifier for the notebook cell. Echoed back in every response so the UI routes updates to the correct cell.

| `namespace`
| String (required)
| Registered namespace name.

| `sql`
| String (required)
| SQL statement to execute.
|===

=== Server → Browser (Outgoing)

The server always sends exactly two messages per query submission.

==== 1. Running (immediate)

Sent before execution begins. The UI should show a spinner at this point.

[source,json]
----
{
  "cellId": "cell-1",
  "status": "running",
  "result": null,
  "error":  null
}
----

==== 2. Done — success

Sent when the query completes successfully.

[source,json]
----
{
  "cellId": "cell-1",
  "status": "done",
  "result": {
    "namespace":       "prod_pg",
    "sql":             "SELECT id, name FROM users LIMIT 10",
    "columns":         ["id", "name"],
    "rows":            [["1", "Alice"], ["2", "Bob"]],
    "executionTimeMs": 38,
    "success":         true,
    "errorMessage":    null
  },
  "error": null
}
----

==== 3. Done — SQL error

If the SQL is invalid or fails at the database level, `status` is still `done` but `result.success` is `false`. The UI renders the error inline in the cell — it does not need to branch on `status`.

[source,json]
----
{
  "cellId": "cell-1",
  "status": "done",
  "result": {
    "namespace":       "prod_pg",
    "sql":             "SELECT * FROM nonexistent_table",
    "columns":         [],
    "rows":            [],
    "executionTimeMs": 5,
    "success":         false,
    "errorMessage":    "ERROR: relation \"nonexistent_table\" does not exist"
  },
  "error": null
}
----

==== 4. Error — infrastructure failure

Sent when the failure is not a SQL error but an infrastructure problem: unknown namespace, missing fields, or a malformed message. No `running` message is sent before an infrastructure error.

[source,json]
----
{
  "cellId": "cell-3",
  "status": "error",
  "result": null,
  "error":  "Unknown namespace: unknown_ns"
}
----

== Error Conditions

[cols="2,3"]
|===
| Condition | Response

| Malformed JSON
| `error` with `cellId: "unknown"` and parse error description

| Missing `namespace` or `sql`
| `error` before any execution attempt

| Unknown namespace
| `error` (executor validates synchronously before submitting to thread pool)

| Invalid SQL / DB-level failure
| `running` then `done` with `result.success: false`

| WebSocket transport error
| `onError` handler sends an `error` message if the session is still open
|===

== Parallel Cell Execution

Multiple cells can be submitted on the same WebSocket connection simultaneously. Each message spawns an independent virtual thread, so responses may arrive out of order. The `cellId` field is used by the frontend to route each response to the correct cell.

[source,json]
----
// Browser sends two queries back-to-back on the same connection
{ "cellId": "cell-A", "namespace": "prod_pg", "sql": "SELECT 1" }
{ "cellId": "cell-B", "namespace": "prod_pg", "sql": "SELECT sleep(2)" }

// Server responds in any order
{ "cellId": "cell-A", "status": "running", ... }
{ "cellId": "cell-B", "status": "running", ... }
{ "cellId": "cell-A", "status": "done",    ... }  // cell-A finishes first
{ "cellId": "cell-B", "status": "done",    ... }
----

== JavaScript Client Example

[source,javascript]
----
const ws = new WebSocket("ws://localhost:8080/ws/query");

ws.onopen = () => {
  ws.send(JSON.stringify({
    cellId:    "cell-1",
    namespace: "prod_pg",
    sql:       "SELECT id, name FROM users LIMIT 10"
  }));
};

ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);

  if (msg.status === "running") {
    showSpinner(msg.cellId);
  } else if (msg.status === "done") {
    hideSpinner(msg.cellId);
    if (msg.result.success) {
      renderTable(msg.cellId, msg.result.columns, msg.result.rows);
    } else {
      renderError(msg.cellId, msg.result.errorMessage);
    }
  } else if (msg.status === "error") {
    hideSpinner(msg.cellId);
    renderError(msg.cellId, msg.error);
  }
};
----

== Implementation Notes

=== Per-Connection Instance + Static Executor

Jakarta WebSocket creates a new `QueryWebsocket` instance for each browser connection. Shared dependencies (`QueryExecutor`) are injected once at startup via a static reference:

[source,java]
----
QueryWebsocket.setExecutor(executor); // called once in HttpServer constructor
----

=== Virtual Threads for Non-Blocking Waits

The WebSocket `@OnMessage` handler runs on a Jetty-managed thread. Blocking that thread on `future.get()` would prevent other messages from being processed on the same connection. A virtual thread is created per in-flight query to wait on the `Future` without consuming a platform thread:

[source,java]
----
Thread.ofVirtual().start(() -> {
    QueryResult result = future.get();
    sendMessage(session, QueryResponse.done(cellId, result));
});
----

=== Jakarta WebSocket + Jetty 12

The endpoint uses the `jakarta.websocket` API and is registered programmatically via `JakartaWebSocketServletContainerInitializer` in `HttpServer`:

[source,java]
----
JakartaWebSocketServletContainerInitializer.configure(context, (ctx, wsContainer) -> {
    wsContainer.addEndpoint(QueryWebsocket.class);
});
----
